\begin{abstract}
This report details the implementation and evaluation of a search-augmented Large Language Model (LLM) agent and a multi-tool realistic agent. We developed an agent capable of utilizing Google Search (via Serper API) to answer open-domain questions, achieving a 44\% Exact Match score on a subset of the Natural Questions dataset, an improvement over the 36\% baseline without search. Furthermore, we extended the agent to support realistic tools including a Calculator, Wikipedia Search, and Weather API, demonstrating its ability to solve complex, multi-step real-world tasks. We also implemented bonus features including a browsing tool and a multi-agent financial analysis system.
\end{abstract}

\section{Part I: Search-Augmented LLM Agent}

\subsection{1. Implementation Logic}

We implemented a ReAct-style agent loop where the model iteratively reasons, selects tools, and processes outputs until a final answer is reached. The core logic handles the conversation history, appends tool outputs, and enforces a strict JSON output format for the final answer to make parsing easier.

The agent stops searching based on two conditions:
\begin{enumerate}
    \item The model outputs a final answer in the requested JSON format (indicating it has sufficient information).
    \item The maximum number of steps (set to 5) is reached to prevent infinite loops.
\end{enumerate}

The main agent loop implementation is shown in Figure~\ref{fig:agent_loop}. The core components are:
\begin{itemize}
    \item \textbf{Message History Management}: Maintains conversation history with system prompt, user query, LLM responses, and tool outputs
    \item \textbf{Tool Calling Logic}: Detects when the LLM requests tools via \texttt{message.tool\_calls}, executes them, and appends results back to the message history
    \item \textbf{Termination Conditions}: Stops when either (1) the LLM outputs a final JSON answer without tool calls, or (2) maximum steps (5) is reached
    \item \textbf{JSON Output Format}: Enforces strict JSON output format using \texttt{response\_format=\{``type'': ``json\_object''\}} to ensure consistent parsing
    \item \textbf{Trajectory Logging}: Records each step (action, query/link, retrieved documents) for later analysis and debugging
\end{itemize}

\subsection{2. Evaluation on Natural Questions}

We evaluated our agent on the Natural Questions (NQ) test set (100 samples) using two metrics: Exact Match (EM) and LLM-as-a-Judge accuracy.

\subsubsection{(1) Baseline Results (No Search)}

The baseline model (DeepSeek-v3.2 without tools) relied solely on its parametric knowledge. It achieved an EM score of 36\% and an LLM Judge accuracy of 74\%.

To reach these scores, we focused on making the base model's outputs align well with the EM evaluation format. Specifically, we (i) enforced a strict JSON-only output with a single \texttt{answer} field using the \texttt{response\_format=\{``type'': ``json\_object''\}} option, and (ii) constrained the answer via the system prompt to be a short entity/date/number instead of a full sentence. Early trials with more free-form answers often produced extra words or explanations that were factually correct but failed EM due to string mismatches; tightening the output format led to the stable 36\% EM and 74\% LLM-judge accuracy.

\subsubsection{(2) Search-Augmented Results}

With the search tool enabled, the agent's EM performance improved significantly: the EM score increased to 44\% (+8\% absolute improvement). However, the LLM Judge accuracy on the same prediction file was 72\%, which is 2 absolute points \emph{lower} than the 74\% baseline without search.

These results satisfy the EM requirement in the project description (the search-augmented agent surpasses the 36\% EM baseline by a clear margin), but they do not meet the requested ``+5 absolute points'' improvement in LLM-judge accuracy.

\textbf{Why the LLM-judge accuracy did not improve by +5 points:}

We believe the LLM-judge accuracy decreased (from 74\% to 72\%) for several reasons:

\begin{enumerate}
    \item \textbf{High baseline performance}: The no-search baseline already achieved 74\% LLM-judge accuracy, which is quite strong. The LLM judge is more lenient than EM and accepts semantically equivalent answers, so many questions were already being answered correctly without search.
    
    \item \textbf{New failure modes introduced}: When search was enabled, some trajectories hit the maximum step limit (5 steps) and returned ``Error: Max steps reached without answer'' instead of an answer. The LLM judge correctly marks these as incorrect, which hurts the accuracy score even though search helped on other questions.
    
    \item \textbf{Search noise}: Sometimes search results contained conflicting or ambiguous information, leading the agent to select incorrect answers from search results rather than relying on its parametric knowledge, which was already correct.
    
    \item \textbf{EM vs LLM-judge mismatch}: Search helped significantly with EM (36\% $\rightarrow$ 44\%) by providing exact string matches for specific dates, names, and numbers. However, the LLM judge is more tolerant—it accepts ``December 1972'' and ``1972'' as equivalent, so the baseline already got many of these ``correct enough'' answers without needing search.
\end{enumerate}

In summary, while search improved exact string matching (EM), it did not improve semantic correctness (LLM-judge) because the baseline was already strong and search introduced some new error cases. The +5 point improvement target may have been optimistic given the high baseline performance.

\section{Part III: Bonus - Browsing Tool}

\subsection{Implementation}

To address the limitation of search snippets, we implemented a `website\_browsing` tool using the Serper scrape API. This allows the agent to read the full text of a URL found during a search, enabling access to detailed information that may not appear in search result snippets.

The browsing tool implementation uses Serper's web scraping endpoint to fetch complete page content. The agent can autonomously decide when to browse a full page versus relying on search snippets, making it particularly useful for questions requiring detailed information from specific web pages.

The implementation (from \texttt{api.py}) is shown in Figure~\ref{fig:browsing_impl}. The function takes a URL, sends a POST request to Serper's scrape API, and returns both the page title and full text content. The content is limited to the first 100,000 characters when passed to the LLM to avoid context overflow.

\begin{figure}[H]
    \centering
    \adjustbox{max width=0.85\textwidth,center}{\includegraphics{api-browsing.png}}
    \caption{Browsing tool implementation from \texttt{api.py}. The function uses Serper's scrape API to fetch full page content from any URL found during search.}
    \label{fig:browsing_impl}
\end{figure}

\subsection{Integration with Agent Loop}

The browsing tool is integrated into the same agent loop as the search tool. The agent follows this workflow:
\begin{enumerate}
    \item Performs a \texttt{google\_search} to find relevant URLs
    \item Evaluates whether the search snippets contain sufficient information
    \item If not, calls \texttt{website\_browsing} with a URL from the search results
    \item Processes the full page content to extract the answer
\end{enumerate}

This two-stage approach (search $\rightarrow$ browse) allows the agent to efficiently gather information: first using fast search to identify relevant pages, then browsing only when necessary to access detailed content.

\subsection{Evaluation and Use Cases}

We found the browsing tool particularly useful for questions like "Who plays the minor character X in show Y?" where the answer might be listed in a table deep within a Wikia page, often missed by the search snippet. In our tests, the browsing tool allowed the agent to verify specific details that were ambiguous in the search results.

\textbf{Example Use Case:} \\
\textit{Question:} "What is the exact release date of the first episode of Breaking Bad?" \\
\textit{Agent Trajectory:}
\begin{enumerate}
    \item \textbf{Search:} \texttt{google\_search(query="Breaking Bad first episode release date")} $\rightarrow$ Returns snippet mentioning "2008" but no specific date
    \item \textbf{Browse:} \texttt{website\_browsing(link="https://en.wikipedia.org/wiki/Breaking\_Bad")} $\rightarrow$ Reads full Wikipedia page
    \item \textbf{Extract:} Finds "January 20, 2008" in the detailed episode information section
    \item \textbf{Answer:} "January 20, 2008"
\end{enumerate}

The browsing tool was integrated into our search-augmented agent (used together with search, not as a separate standalone agent). We evaluated the agent with both search and browsing capabilities enabled. The results are shown in Table~\ref{tab:browsing_results}.

    \item Some browsing attempts failed or returned irrelevant content, offsetting the benefits.
\end{itemize}

However, browsing was still valuable because it allowed the agent to access precise information that search snippets could not provide, particularly for questions requiring specific details from structured content (tables, lists) within web pages. In practice, the browsing tool serves as a ``safety net'' that the agent can use when search snippets are insufficient, even if it doesn't dramatically change aggregate metrics.

\section{Part IV: Bonus - Multi-Agent Financial Analysis}

Because we wanted to have more fun with the concepts learned in this course, we designed an additional experiment involving a \textbf{Multi-Agent System} for financial valuation. 

\subsection{Architecture}

We created a "Committee" of three specialized agents, each with distinct roles and perspectives, to debate the valuation of a public company (NVIDIA Corp.):

\begin{enumerate}
    \item \textbf{Lead Quantitative Analyst (Base Case)}: A tool-augmented agent that uses `google\_search` and `website\_browsing` to find real-time financial metrics (FCF, Beta, Risk-Free Rate, shares outstanding) and calculate a Discounted Cash Flow (DCF) valuation. This agent performs the initial data gathering and quantitative analysis.
    \item \textbf{Senior Growth Strategist (Bull)}: A reasoning-only agent that critiques the base case by arguing for higher growth scenarios (e.g., AI Total Addressable Market expansion, market dominance) and proposes an adjusted, higher target price with a "BUY" recommendation.
    \item \textbf{Chief Risk Officer (Bear)}: Another reasoning-only agent that critiques the base case by highlighting downside risks (competition, cyclicality, geopolitical factors) and proposes a lower target price with a "SELL" recommendation.
\end{enumerate}

\subsection{Implementation Details}

The financial agent implementation is shown in Figure~\ref{fig:fin_agent_impl}, which demonstrates the core function that runs the Lead Quantitative Analyst agent. The agent uses a specialized prompt that guides it through the DCF valuation process, including data gathering, market sentiment analysis, assumption determination, and calculation.

\begin{figure}[H]
    \centering
    \adjustbox{max width=0.85\textwidth,center}{\includegraphics{fin-agent.png}}
    \caption{Financial agent implementation from \texttt{bonus/financial\_agent.py} showing the \texttt{run\_financial\_agent()} function. The function sets up the specialized financial analyst prompt, formats it with current date and ticker information, and runs the agent loop with up to 40 tool-calling steps. The agent is explicitly instructed to use tools for all data gathering and calculations, ensuring it relies on real-time information rather than parametric knowledge.}
    \label{fig:fin_agent_impl}
\end{figure}

The multi-agent system operates in three sequential rounds:

\textbf{Round 1: Data Gathering and Base Valuation} \\
The Lead Quantitative Analyst agent is initialized with a specialized financial analyst prompt that instructs it to:
\begin{itemize}
    \item Gather current financial data (stock price, shares outstanding, free cash flow, net debt, beta, risk-free rate)
    \item Research market sentiment (Reddit discussions, recent news)
    \item Determine growth assumptions based on analyst consensus and industry trends
    \item Calculate WACC (Weighted Average Cost of Capital) using the formula: Risk-Free Rate + Beta $\times$ 5.0\%
    \item Perform a 5-year DCF valuation with terminal value
    \item Output a structured JSON with reasoning, assumptions, and valuation
\end{itemize}

This agent uses up to 40 tool-calling steps, autonomously deciding when to search, browse websites, and perform calculations. The agent is constrained to use tools for all data gathering and calculations, ensuring it relies on real-time information rather than parametric knowledge.

\textbf{Round 2 \& 3: Critique and Debate} \\
The Bull and Bear agents are reasoning-only agents (no tool access) that receive the base case JSON output. Each agent is given a specific persona and bias:

\begin{itemize}
    \item \textbf{Bull Agent Prompt}: "Optimistic. Focus on AI total addressable market (TAM) expansion and monopoly pricing power."
    \item \textbf{Bear Agent Prompt}: "Pessimistic. Focus on competition, overvaluation, and cyclical semiconductor risks."
\end{itemize}

These agents critique the base case assumptions (growth rate, WACC, terminal growth) and propose adjusted valuations. They output structured JSON with critiques, proposed adjustments, new target prices, and investment recommendations (BUY/SELL/HOLD).

\begin{lstlisting}[caption={Multi-Agent System Flow}, label={lst:multi_agent}]
# Round 1: Lead Analyst (Tool-Augmented)
base_case = run_financial_agent(ticker="NVDA", max_steps=40, 
                                persona="Lead Quantitative Analyst")

# Round 2: Bull Strategist (Reasoning Only)
bull_case = get_critique(base_case, 
                        persona="Senior Growth Strategist",
                        bias="Optimistic. Focus on AI TAM expansion...")

# Round 3: Bear Strategist (Reasoning Only)
bear_case = get_critique(base_case,
                        persona="Chief Risk Officer", 
                        bias="Pessimistic. Focus on competition...")
\end{lstlisting}

The system demonstrates how different agent personas can provide diverse perspectives on the same quantitative analysis, simulating a real investment committee debate where multiple viewpoints are considered before making decisions.

\subsection{Case Study: NVIDIA (NVDA)}
On November 27, 2025, we ran the system on NVIDIA. The agents retrieved live data (Price: \$179.51, Beta: 2.27) and engaged in a debate. Below is the final committee report and the detailed process log of the lead analyst.

\subsubsection{Investment Committee Report}

\textbf{Multi-Agent Investment Committee Report: NVDA} \\
\textbf{Date}: 2025-11-27

\paragraph{1. Lead Analyst (Base Case)}
\begin{itemize}
    \item \textbf{Valuation}: \$65.45
    \item \textbf{Upside}: -63.54\%
    \item \textbf{Reasoning}: The DCF valuation suggests NVDA is significantly overvalued at current prices, primarily due to the high WACC (15.39\%) driven by NVDA's elevated beta of 2.27. While the company continues to show strong growth in data center revenue (66\% YoY in Q3), the current stock price appears to already reflect substantial future growth expectations. The conservative 36\% growth rate assumption, while high, is below recent actual growth rates, and the high cost of capital makes future cash flows less valuable in present terms.
    \item \textbf{Thinking Process}: \textit{I gathered data from multiple sources: Current stock price from Robinhood (\$179.51), shares outstanding from Macrotrends (24.532B), FCF from Macrotrends (\$60.853B annual 2025), net debt from Yahoo Finance (\$6.6B), beta from Investing.com (2.27), and risk-free rate from FRED (4.04\%). For growth rate, I used 36\% based on Seeking Alpha's analysis of data center growth through 2030, which is conservative given NVDA's recent 66\% YoY growth. \paragraph{2. The Debate}

\textbf{Senior Growth Strategist (Bull)}
\begin{itemize}
    \item \textbf{Critique}: The original DCF analysis is overly conservative and fails to adequately account for NVIDIA's dominant position in the AI infrastructure market. The 36\% growth rate assumption, while high by traditional standards, is actually conservative given NVIDIA's recent 66\% YoY growth and the massive AI TAM expansion. The AI chip market is projected to grow from \$30B in 2023 to over \$400B by 2032, and NVIDIA commands 80-90\% market share in AI training chips. The WACC of 15.39\% is excessively high - NVIDIA's strong cash flow generation, market leadership, and pricing power should command a lower risk premium. The beta of 2.27 likely overstates systematic risk given NVIDIA's defensive characteristics in the AI ecosystem. The terminal growth rate of 2.5\% is too low for a company with NVIDIA's durable competitive advantages and long-term growth runway in AI.
    \item \textbf{Adjustment}: Increase growth rate to 45\% for the next 5 years to better reflect AI market expansion and NVIDIA's pricing power, reduce WACC to 12\% given strong cash flow stability and market position, and increase terminal growth to 3.5\% to account for long-term AI adoption tailwinds.
    \item \textbf{Target}: \$215.75
    \item \textbf{Vote}: BUY
\end{itemize}

\textbf{Chief Risk Officer (Bear)}
\begin{itemize}
    \item \textbf{Critique}: The original DCF valuation fails to adequately account for several critical risk factors. First, the 36\% growth rate assumption is excessively optimistic given intensifying competition from AMD, Intel, and custom silicon development by major cloud providers (Google TPU, Amazon Trainium). The semiconductor industry is notoriously cyclical, and we're likely approaching peak AI chip demand. Second, the WACC calculation is problematic - using a flat 5\% market risk premium ignores current market volatility and sector-specific risks. The terminal growth rate of 2.5\% may be too high given eventual market saturation and technological disruption. Third, the valuation doesn't sufficiently discount for geopolitical risks (China restrictions, Taiwan tensions) and potential regulatory scrutiny of AI dominance. The current stock price appears to be pricing in near-perfect execution for the next decade, which is highly improbable in this competitive landscape.
    \item \textbf{Adjustment}: Reduce growth rate to 20\% for the first 3 years, declining to 8\% thereafter, reflecting competitive pressures and market saturation. Increase WACC to 18\% to better capture semiconductor sector volatility and company-specific risks. Maintain terminal growth at 2\% given long-term industry normalization.
    \item \textbf{Target}: \$42.75
    \item \textbf{Vote}: SELL
\end{itemize}

\subsection{Key Insights}

The multi-agent financial analysis experiment revealed several important insights:

\begin{itemize}
    \item \textbf{Specialization Works}: By giving each agent a distinct role (data gatherer, optimist, pessimist), we obtained more nuanced analysis than a single agent could provide. The tool-augmented Lead Analyst focused on quantitative accuracy, while the reasoning-only Bull and Bear agents provided qualitative perspectives.
    \item \textbf{Structured Outputs Enable Collaboration}: Using structured JSON outputs allowed the agents to share information effectively. The base case JSON served as a common data structure that both critique agents could analyze and build upon.
    \item \textbf{Real-World Applicability}: The system successfully retrieved real-time financial data, performed complex DCF calculations, and generated investment committee-style reports. This demonstrates the potential for LLM agents to assist in professional financial analysis workflows.
    \item \textbf{Debate and Perspective}: The wide range of valuations (\$42.75 to \$215.75) from the same base data highlights how different assumptions and perspectives can lead to dramatically different conclusions—a realistic reflection of how investment committees operate.
\end{itemize}

\section{Conclusion}

This project showed us how adding external tools to LLMs can make them much more useful. The base model knows a lot, but adding Search and custom tools (Weather, Calculator, Wikipedia) lets it actually verify facts, get real-time data, and do calculations.

What we accomplished:
\begin{itemize}
    \item Got 44\% Exact Match on Natural Questions with search (+8\% over the 36\% baseline)
    \item Built a multi-tool agent that can chain Wikipedia, Weather API, and Calculator to solve multi-step tasks
    \item Added a browsing tool so the agent can read full web pages, not just search snippets
    \item Created a multi-agent system for financial analysis where different agents debate valuations
\end{itemize}

The multi-agent experiment was fun to build and shows how you could use this approach for other domains where you want different perspectives, like legal analysis or medical diagnosis. Overall, we learned that tool-augmented agents are way more capable than base LLMs alone.
